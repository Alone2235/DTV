## 根因定位（用户要求查"回退推荐页"的真正原因）

三层因果链（全部代码实锤）：
1. 死因：自杀定时器（playedCount>=4 → onPrepared 后 1.5s killProcess）在第 5 个加载途中引爆；或固件第 5 次起播杀（已有 KILLCHASE 铁证）。
2. **回推荐页主因**：MainActivity.tryRestorePlayback 的 30s 恢复窗口（MainActivity.kt:172）拿 resume JSON 的 ts 算，而 ts 只在 PlayerActivity.onPrepared → saveResumeState 时写一次 = 上一个视频起播时刻，不是死亡时刻。看视频 >30s 再下滑死亡 → ts 过期 → clearResume → 落推荐页且无法恢复。这解释了"偏偏第 4/5 个出现"（前几个不死，死的时候 ts 已老）。
3. **循环打不破**：MainActivity.kt:197 retry+1 从不写回 Prefs，saveResumeState 恒写 retry=0 → "连续崩 2 次强制 VLC（engine=3）"是死代码 → IJK 同位置反复死。

FeedBus 是纯内存总线，进程死后唯一恢复路径就是 Prefs resume JSON。

修复方案：①progressTick 里周期刷新 resume 的 ts 或窗口放宽到 5 分钟；②retry 写回 Prefs 让熔断生效；③自杀时机挪到 playCurrent() 开头。
等用户确认后动手。

## 回归：改完后变成"第 4 个下滑就黑屏、不加载、回推荐页"（更严重）

用户反馈：上一版修复后，第 4 个下滑直接黑屏、连加载都不加载、然后黑屏回推荐页。

**真正根因（比之前更底层）**：崩溃恢复状态全部用 `SharedPreferences.apply()` 存（和 Cookie 同一个 douyin_tv_prefs 文件）。apply() 先改内存、异步落盘。`restartSelf()` 里 saveResumeState + markPlannedRestart 之后**立刻 killProcess**，异步写盘线程来不及跑 → 恢复点/心跳/计划重启标记全丢在内存 → 冷启动 loadResume 拿空 → 判"无恢复点"→ 回推荐页。固件杀进程同理。**恢复机制从来没真正把状态写到盘上，一直没生效过**——这也解释了最初"固件杀第 5 个必回推荐页"。

**修复（Prefs.kt 崩溃恢复部分重写，SharedPreferences → 普通文件 + 同步写）**：
- File.writeText 是同步的，close() 后数据进内核页缓存；进程死了页缓存仍在（内核负责回写 flash，与进程无关）→ 进程死亡不丢数据。
- resume.json（saveResume/loadResume/clearResume，tmp+rename 原子替换）、resume_alive（心跳）、planned_restart、crash_streak 四个小文件，全部同步写。
- 新增 Prefs.trace() → filesDir/restore_trace.txt（电视没 logcat，靠它拿地面真值），在 COLD_START / RESTORE(expired|empty_items|planned|parse_fail) / RESTART_GUARD / SELF_KILL 各节点埋点。
- 所有 Prefs 函数签名不变 → 调用方（PlayerActivity/MainActivity）零改动。

验证：`./gradlew.bat :app:compileDebugKotlin --offline` → BUILD SUCCESSFUL。
真机验证：跑一遍后拉 filesDir/restore_trace.txt：
- 正常应看到 `SELF_KILL ... -> 已同步落盘` 紧跟 `COLD_START resume_blank=false` + `RESTORE planned=true idx=N -> 播放页`（回到要播那条）。
- 若还回推荐页，trace 会写明是 expired / empty_items / parse_fail / resume_blank=true 哪一种 → 不再是猜。

## 现状：不崩了，但每 4 个视频黑屏几秒（自杀重启的固有开销）

用户实测：恢复链路已通，不再回推荐页；代价是每 4 个视频一次进程自杀重启 → 冷启动 → 恢复 → 重新起播，中间黑屏几秒。

排查黑屏构成：进程 spawn + Application init（固定成本）+ MainActivity setContentView/bindViews/setupNav/setupGrid(RecyclerView)（恢复直通时全白做）+ PlayerActivity 布局 + IJK .so 加载 + 网络首缓冲。引擎 4 个构造都轻量（native 初始化都在 prepare 里，只跑选中的那个）→ 无需懒加载重构。

**已做优化（编译通过）**：
1. MainActivity.onCreate 恢复检查挪到 setContentView **之前**（ensureUi()/uiReady 延迟建 UI）；恢复直通时 skipNextResumeUi=true，紧接着那次 onResume 路过不建；从播放页返回时 onResume 补建 UI + loadFeed。省去重启路径上的首页布局+列表初始化+拉推荐流。

## 根源之问：能不能不靠自杀重启

分层结论：恢复层（apply→文件同步写）已根治；自杀重启是"第 5 个必死"的 workaround。

**"第 5 个必死"的根源假设 = IJK per-play native 泄漏**（非"固件计数"）。Engines.kt 注释里的铁证：
- IJK 两条路都在 ~5 个死：release+new 漏 OMX node/线程；reset() 复用漏 codec 内部资源（80.1）。均 LMK 杀、无 tombstone。
- "Exo 在这台机器上不崩，正是因为复用实例（setMediaSource 换源）"（Engines.kt:522）。
- "VLC 不崩（不碰 OMX 释放竞态），但声音差"（MainActivity 熔断注释）。
→ 即只有 IJK 漏；自杀机制存在的唯一原因是"IJK 最流畅"。

**矛盾点**：用户随后把自杀回滚为"无条件（IJK 与 Exo 都走）"（playCurrent 注释"回滚 81.5"）——若用户有 Exo 也会死的新证据，则"固件/进程级"为真、泄漏假设错。此矛盾只能靠数据裁决，我没动用户的回滚。

**已埋探针（编译通过）**：PlayerActivity.snapMem(tag)——每个视频起播往 mem_log.txt 追加一行 `PLAY#n idx=m rss=X vmsize=X native=X java=X fd=N`（/proc/self/status + /proc/self/fd + NativeHeap）。onPrepared 里调用。

**测试协议（待真机跑）**：每个引擎（IJK/Exo/VLC）各连刷 8-10 个视频 → 拉 mem_log.txt 看 PLAY# 曲线：
- IJK 涨、Exo/VLC 平 → 泄漏 IJK 特有 → 根治 = 默认引擎换 Exo（或修 VLC 声音），自杀仅留 IJK 或直接退役。
- 全都涨 → 固件/进程级为真 → 自杀即正解，进一步优化走双进程轮换。
- 中间插曲：我给 snapMem 加函数时漏了收尾大括号导致一次编译失败（函数嵌套级联错误），已补上并 BUILD SUCCESSFUL。
